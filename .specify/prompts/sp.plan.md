# Implementation Plan: Repository Analysis Pipeline

**Branch**: `001-repository-analysis-pipeline` | **Date**: 2026-07-10 | **Spec**: [spec.md](./spec.md)
**Input**: Feature specification from `/specs/001-repository-analysis-pipeline/spec.md`

## Summary
Build the core repository analysis pipeline that clones GitHub repositories, parses source files using tree-sitter AST parsers, extracts dependencies and symbols, detects frameworks, constructs architecture and knowledge graphs, and persists results to SQLite for LLM querying. The pipeline must be modular, testable, and support incremental re-analysis.

## Technical Context

**Language/Version**: Python 3.11+
**Primary Dependencies**: 
- Textual (TUI framework)
- Rich (terminal formatting)
- tree-sitter + tree-sitter-language-bindings (AST parsing)
- GitPython or pygit2 (git operations)
- NetworkX (graph construction)
- SQLModel or raw sqlite3 (persistence)
- httpx (async HTTP for GitHub API)
- pydantic (data validation)

**Storage**: SQLite (local file: `~/.gitreverse/cache.db`)
**Testing**: pytest + pytest-asyncio + pytest-cov
**Target Platform**: macOS, Linux (Windows in V1.1)
**Project Type**: CLI application with TUI
**Performance Goals**: 
- Clone + analyze 10k LOC repo: <60s
- Knowledge graph query: <100ms
- Memory: <500MB for <100k LOC repos

**Constraints**: 
- No blocking I/O in main event loop
- All network operations must be async
- Progress reporting must not slow down analysis
- Cancellation must be immediate (no orphaned processes)

**Scale/Scope**: 
- Support repositories up to 1M LOC (with chunking)
- Support 50+ programming languages (via tree-sitter grammars)
- Support monorepos with multiple packages

## Phase 0: Research & Unknowns

### Unknowns to Resolve

1. **tree-sitter Python bindings stability**: Are the official tree-sitter Python bindings stable enough for production use, or should we use a wrapper like `tree-sitter-languages`?
   - **Research task**: Benchmark tree-sitter vs tree-sitter-languages for parsing speed, memory usage, and language support.
   - **Decision needed**: Which library to use for AST parsing.

2. **SQLite concurrency model**: Python's sqlite3 module has limitations with concurrent writes. Should we use a connection pool, WAL mode, or a higher-level library like SQLModel?
   - **Research task**: Test SQLite performance under concurrent analysis tasks.
   - **Decision needed**: Database access strategy.

3. **Git library choice**: GitPython vs pygit2. GitPython is pure Python (easier install) but slower. pygit2 is a binding to libgit2 (faster) but requires compilation.
   - **Research task**: Benchmark clone speed, memory usage, and cross-platform compatibility.
   - **Decision needed**: Which git library to use.

4. **Incremental analysis strategy**: How to detect changed files efficiently? Use `git diff` with cached commit hashes, or file modification times?
   - **Research task**: Compare git diff vs mtime for change detection accuracy and speed.
   - **Decision needed**: Incremental analysis algorithm.

5. **Knowledge graph storage format**: Store as adjacency list in SQLite, or use a dedicated graph database (e.g., NetworkX in-memory + SQLite persistence)?
   - **Research task**: Benchmark query performance for graph traversals (e.g., "find all dependencies of symbol X").
   - **Decision needed**: Graph storage and query strategy.
